## Запуск у Docker

Єдина команда піднімає застосунок разом із SQL Server:

```bash
cp .env.example .env
docker compose up --build
```

API: `http://localhost:8080/swagger`

Змінні оточення задаються у файлі `.env` (він не потрапляє до репозиторію):

| Змінна           | Призначення                                              |
| ---------------- | -------------------------------------------------------- |
| `DB_PASSWORD`    | Пароль `sa` для SQL Server                               |
| `JWT_KEY`        | Ключ підпису токенів, щонайменше 32 символи              |
| `ADMIN_EMAIL`    | Пошта адміністратора, що створюється при першому запуску |
| `ADMIN_PASSWORD` | Його пароль                                              |

Зупинка зі збереженням даних:

```bash
docker compose down
```

Повне очищення разом із базою:

```bash
docker compose down -v
```

### Рішення в конфігурації контейнерів

- **Багатоетапна збірка**: у фінальний образ потрапляє лише runtime і опубліковані
  файли, без SDK та вихідного коду.
- **Chiseled-образ** `aspnet:10.0` не містить пакетного менеджера й оболонки,
  важить удвічі менше звичайного і має суттєво менше вразливостей.
  Процес працює від непривілейованого користувача `app`.
- **`.csproj` копіюються окремим шаром** до решти коду: поки залежності
  не змінилися, `dotnet restore` береться з кешу.
- **Healthcheck на базі**: API стартує лише після того, як SQL Server
  реально приймає запити, інакше міграції впали б на старті.
- **Порт бази назовні не публікується**: доступ до SQL Server можливий лише
  з внутрішньої мережі compose, що звужує поверхню атаки.
