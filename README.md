# Conference Booking API

API для управління конференц-залами, бронюваннями та розрахунком вартості оренди.

## Швидкий старт

```bash
git clone https://github.com/dolbolesya/conference-booking.git
cd conference-booking
dotnet run --project ConferenceBooking.API
```

База створюється автоматично (LocalDB), міграції застосовуються при старті,
початкові дані з ТЗ додаються при першому запуску: три зали й три послуги.

Документація API: `https://localhost:7228/swagger`

Адміністратор створюється автоматично. Облікові дані задаються в секції `Seed`
конфігурації, за замовчуванням `admin@local.com` / `Admin12345`.
Звичайні користувачі реєструються через `POST /api/auth/register`.

## Бізнес-завдання

Компанія здає конференц-зали погодинно. Вартість залежить від часу доби:
ранкові години дешевші на 10%, вечірні на 20%, пікові (12:00-14:00) дорожчі на 15%.
До залу можна замовити додаткові послуги: проєктор, Wi-Fi, звук.

## Технічні рішення

### Посегментний розрахунок вартості

Ключова складність задачі. Бронювання 10:00-14:00 це **не** «4 години за базовою
ставкою»: з 10:00 до 12:00 діє стандартний тариф, з 12:00 до 14:00 піковий.
Інтервал ріжеться по межах тарифних вікон, кожен відрізок тарифікується окремо:

```
10:00 ──── 12:00 ──── 14:00
  2 год × 1.00   2 год × 1.15
    4000 грн       4600 грн     = 8600 грн
```

Тариф відрізка визначається за його серединою: відрізок за побудовою не перетинає
меж, тому будь-яка внутрішня точка однозначно ідентифікує вікно. Накладання вікон
(пікові лежать усередині стандартних) розв'язується пріоритетом.

Тарифи винесені в `appsettings.json`, тож бізнес змінює знижки без релізу.

### Захист від подвійного бронювання

Перевірка «чи вільний зал» і вставка броні виконуються в одній транзакції
з рівнем ізоляції Serializable. Без цього два одночасні запити на один зал
обидва побачили б «вільно» і обидва створили б бронь.

Інтервали напіввідкриті `[Start, End)`, тому бронювання 10:00-12:00 і 12:00-14:00
не конфліктують.

### Власність бронювань

Дані замовника не передаються в тілі запиту, вони беруться з JWT. Інакше будь-хто
міг би створити бронь від чужого імені або скасувати чужу, знаючи лише її
ідентифікатор. Перевірка прав живе в домені (`Booking.EnsureOwnedBy`), щоб її
не можна було обійти з іншого сценарію.

### Незмінність історії

- Бронювання зберігає **знімок** послуги (назву й ціну), а не посилання.
  Підвищення ціни проєктора не переписує вже виставлені рахунки.
- Зали й послуги видаляються м'яко (`IsDeleted`), інакше зруйнувалася б
  історія бронювань і фінансова звітність.
- Користувача з бронями не можна видалити (`DeleteBehavior.Restrict`).

### Архітектура

Чотири проєкти, залежності йдуть в один бік:

```
API → Infrastructure → Application → Domain
```

- **Domain** - сутності та бізнес-правила. Нуль зовнішніх залежностей:
  не знає ні про базу, ні про HTTP.
- **Application** - сценарії використання, DTO, валідація.
- **Infrastructure** - EF Core, доступ до БД, хешування, системний час.
- **API** - контролери, автентифікація, обробка помилок.

Багата доменна модель: властивості мають приватні сеттери, зміни відбуваються
лише через методи, які перевіряють інваріанти. Створити зал із від'ємною
місткістю неможливо, і це не «не рекомендується», а саме неможливо.

### Патерни

| Патерн | Застосування |
|---|---|
| Strategy | `IPricingPolicy`, правила тарифікації за інтерфейсом; сезонні тарифи додаються новим класом |
| Value Object | `TimeRange`, проміжок часу без ідентичності, завжди валідний |
| Aggregate Root | `Room`, `Booking`, єдині точки входу для змін |
| Factory Method | `Booking.Create`, усі перевірки в одному місці |
| Repository + UoW | Реалізовані EF Core: `DbSet` і `DbContext` |
| Options | `PricingOptions`, типізований доступ до конфігурації |

**Свідомо не використані:** MediatR, AutoMapper, CQRS, власний Repository поверх
EF Core, ASP.NET Core Identity. На обсязі цієї задачі вони додають шар непрямої
адресації без виграшу.

### Безпека

- Паролі хешуються BCrypt (work factor 12): сіль генерується автоматично,
  перебір лишається дорогим навіть при витоку бази.
- JWT з розподілом ролей: керування залами та звіти для `Admin`,
  бронювання для автентифікованих користувачів, перегляд залів
  і розрахунок вартості публічні.
- Вхід повертає однакову помилку для неіснуючої пошти й невірного пароля,
  щоб неможливо було перебором з'ясувати, хто зареєстрований.
- Rate limiting: 100 запитів/хв на IP глобально, 10/хв на створення бронювань,
  5/хв на вхід і реєстрацію.
- Усі помилки повертаються у форматі ProblemDetails (RFC 9457) з машинозчитуваним
  кодом. Деталі внутрішніх помилок назовні не потрапляють, лише в лог.
- Валідація вхідних даних (FluentValidation) до звернення до домену та БД.

> У продакшені ключ підпису JWT і пароль адміністратора мають зберігатися
> у змінних оточення або Key Vault, а не в `appsettings.json`.
> Видача токенів виноситься до зовнішнього провайдера (Keycloak, Auth0):
> код застосунку при цьому змінюється мінімально, `AddJwtBearer` перемикається
> з симетричного ключа на `Authority` провайдера.

## Звіти

| Ендпоінт | Питання бізнесу |
|---|---|
| `GET /api/reports/revenue` | Скільки заробили, який зал окупається |
| `GET /api/reports/utilization` | Що простоює, чи не змінити ціну |
| `GET /api/reports/amenities` | Чи варто докупити ще один проєктор |
| `GET /api/reports/hourly` | Чи правильно виставлені пікові години |

Агрегація виконується в пам'яті: для обсягів цього завдання це простіше
й передбачуваніше. При зростанні даних звіти переносяться у SQL-подання.

## Допущення

ТЗ не уточнює низку моментів. Прийняті рішення:

- **Послуги оплачуються разово за бронювання**, не погодинно (у ТЗ ціна без прив'язки до часу).
- **Бронювання лише в межах 06:00-23:00**, тарифні вікна покривають саме цей діапазон.
- **Мінімальна тривалість 30 хвилин, крок 30 хвилин**, що дозволяє бронь на 1.5 год.
- **Бронювання не переходить через добу** як наслідок робочих годин.
- **Скасування можливе до початку** броні. У ТЗ не описане, але без нього система нежиттєздатна.
- **Ролі та реєстрація** в ТЗ не описані, запропоновані самостійно.
- **Попередній розрахунок вартості** (`POST /api/bookings/quote`): клієнт має бачити ціну до підтвердження.
- Пошук залів і розрахунок вартості зроблені через `POST`, а не `GET`: параметрів багато,
  включно зі списком послуг.
